# CASE-002 — Minimal System-Centric Collective Learning

**Project:** Intelligence Spillover, Generalization, Fluidity, Transfer, and Relay (ISGFTR)  
**Document type:** Illustrative research case and falsifiable experimental protocol  
**Version:** 1.0.0 (theory-first)  
**Status:** Proposed experiment; no empirical results claimed  
**Date:** 2026-10-30  
**Related documents:** ISGFTR-006, ISGFTR-007, ISGFTR-008, ISGFTR-009, ISGFTR-010; SPEC-001–004; CASE-001

## Abstract

This case examines whether a small system of individually limited, **frozen execution units** can exhibit measurable and durable *system-level learning* through changes in routing, shared evidence, coordination rules, and structural memory. The proposed laboratory uses three to five bounded agents to solve a sequence of related but nonidentical tasks. No component model is fine-tuned during the main experiment. Instead, an independently governed learning layer updates explicit system structures after each trial. The central question is not whether a multi-agent system can outperform a single agent on one task, but whether experience produces **persistent, transferable improvements** beyond the effects of added compute, prompt length, memorization, or fixed ensembling.

The case specifies capability boundaries, task families, a minimal architecture, learning interventions, controlled baselines, an evaluation plan, negative-result handling, and relay records. It does not assert that system-centric learning is equivalent to intrinsic model learning, recursive self-improvement, or artificial general intelligence.

## 1. Research Motivation

A model's weights are one possible location for learning, but not the only location where a system can store and exploit experience. A team may learn which member handles a problem, which sequence of actions is reliable, which failure patterns recur, and which evidence should be retained—even if the skills of each member remain unchanged. The distinction matters for structural intelligence research because **execution units** and **learning units** need not be identical.

A single successful orchestration is not enough to establish learning. The proposed experiment therefore asks whether an initially naive organization becomes better across held-out task instances and modest domain shifts, and whether the improvement survives removal of irrelevant historical details.

The case is intentionally small. A minimal system makes attribution, ablation, cost accounting, and independent reproduction more feasible than a large opaque multi-agent deployment.

## 2. Research Questions

- **RQ1 — System learning:** Can a frozen-unit system improve held-out performance through updates to explicit organizational structures alone?
- **RQ2 — Attribution:** Which gains come from routing, shared evidence, task decomposition, or verification rather than increased inference budget?
- **RQ3 — Transfer:** Do learned structural rules transfer to new task templates or domains with shared constraints?
- **RQ4 — Durability:** Do gains persist across sessions, agent restarts, and replacement of task-specific examples?
- **RQ5 — Relay:** Does recording both positive and negative outcomes improve subsequent decisions over storing successful examples alone?
- **RQ6 — Boundaries:** When does organizational learning plateau, fail, or create negative transfer?

## 3. Scope and Working Definitions

**Execution unit:** A frozen component that performs a bounded action, such as planning, checking constraints, retrieving evidence, or producing an answer. Its underlying parameters and permitted tools remain fixed within an experimental condition.

**Learning unit:** A process that modifies a persistent artifact based on evaluated outcomes. In this case it updates routing policies, decomposition templates, evidence summaries, and error-prevention rules, but does not modify execution-unit weights.

**Structural memory:** A versioned store of reusable, task-independent patterns and their applicability conditions. It is distinct from a transcript dump or unrestricted retrieval of past answers.

**System-level learning:** A statistically credible improvement on held-out tasks attributable to experience-dependent changes in persistent system structures, relative to matched controls.

**Collective learning:** Evidence-based improvement arising from information generated by multiple units or trials and reused by the system, with provenance and failure cases preserved.

**Durable growth:** Improvement retained across fresh sessions and evaluated beyond the exact tasks used to create the structural update. It is stronger than a one-off performance increase.

These are operational definitions for this case, not universal definitions of intelligence.

## 4. Minimal Experimental System

The reference design uses four execution units and one learning/control function. A three-unit version can combine roles; a five-unit version can split evidence retrieval and verification.

| Component | Bounded role | Mutable during main experiment? |
|---|---|---|
| **U1 — Task Interpreter** | Extract task goals, constraints, and uncertainty | No |
| **U2 — Planner** | Produce a candidate sequence or allocation | No |
| **U3 — Constraint Checker** | Detect violations and identify counterexamples | No |
| **U4 — Reporter** | Assemble a final, auditable answer | No |
| **L — Structural Learning Controller** | Update routing, decomposition, evidence registry, and applicable policies | Yes, under a fixed update contract |

A deterministic task evaluator should be used where feasible. The controller may select a different execution path in future trials, but may not secretly replace or fine-tune the frozen units. All changes are logged with before/after versions.

### 4.1 A bounded task family

A suitable initial domain is **small resource-constrained scheduling**: assign jobs to workers or machines subject to deadlines, precedence, availability, and cost constraints. A second domain is **software maintenance planning**, where fixes have dependencies, test requirements, and limited engineering capacity. Both can be generated with hidden ground-truth feasibility checks and controlled difficulty.

The common structural core includes dependency graphs, constraint satisfaction, prioritization, and verification. Domain-specific residuals—such as human availability versus software regression risk—must be preserved rather than erased by analogy.

### 4.2 What is allowed to change

Allowed persistent updates include:

1. A routing rule mapping task features to a permitted execution path.
2. A decomposition template with explicit preconditions.
3. A compact failure signature and corresponding verification step.
4. A confidence or evidence-quality label, with calibration claims separately tested.
5. A precedent link identifying tasks where the structure succeeded or failed.

Prohibited changes in the frozen-unit condition include model fine-tuning, unlogged tool changes, expanding the task-specific context beyond the matched budget, and inserting exact held-out answers into memory.

## 5. Learning–Execution Decoupling

The main hypothesis is architectural: an execution unit can remain unchanged while a separate layer learns how and when to use it. For example, a controller might discover that precedence-heavy scheduling tasks benefit from constraint checking *before* final reporting, whereas unconstrained tasks do not justify the extra call. Such a rule is organizational learning only if it is inferred from prior evaluated trials, persists, and generalizes to unseen instances.

This separation must not be exaggerated. An updated prompt template may effectively encode a new program, and a large structural memory may supply substantial external knowledge. Those are legitimate system changes but are not evidence that the original model gained intrinsic ability. The evaluation should report model-level and system-level capability claims separately.

## 6. Proposed Learning Loop

```text
Task intake
   ↓
Task features and scoped capability profile
   ↓
Policy selects execution path
   ↓
Frozen units execute and exchange bounded artifacts
   ↓
Independent evaluator measures outcome, cost, and errors
   ↓
Evidence bundle records success, failure, uncertainty, provenance
   ↓
Learning controller proposes a structural update
   ↓
Gate A: update admissibility and resource/safety constraints
   ↓
Sandbox retest against held-out and regression tasks
   ↓
Gate B: evidence-based adoption decision
   ↓
Versioned structural relay into next trial
```

The update loop may also reject a proposed change. Repeated execution is a potential **temporal evidence relay**, not automatically a positive learning event.

## 7. Experimental Conditions and Baselines

To avoid conflating additional computation with learning, compare the following conditions under matched task distribution and, where possible, token, call, and wall-clock budgets.

| ID | Condition | Persistent adaptation | Purpose |
|---|---|---|---|
| B0 | Single frozen execution unit | None | Minimal individual baseline |
| B1 | Fixed multi-unit pipeline | None | Measure static coordination benefit |
| B2 | Fixed pipeline with more inference budget | None | Control for compute scaling |
| B3 | Random or heuristic routing | None | Control for nonlearned flexibility |
| B4 | Transcript retrieval | Historical examples only | Test memorization/retrieval effects |
| E1 | Learned routing only | Routing rules | Isolate routing learning |
| E2 | Learned decomposition and checks | Templates and verification policies | Isolate structural adaptation |
| E3 | Full evidence-aware structural relay | Rules, failures, provenance, bounded memory | Main proposed condition |
| A1 | E3 without negative evidence | Positive results only | Test value of counterevidence |
| A2 | E3 with shuffled outcomes | Invalid credit assignment | Test dependence on valid feedback |

Ablations should preserve comparable memory size when feasible. If the full condition has more computational resources, report both raw performance and cost-normalized performance rather than asserting an unqualified advantage.

## 8. Task Construction and Leakage Controls

Generate task instances from several distinct templates with independently sampled variables. Partition by **template family**, not merely by random instance, so that the test set contains genuinely unseen structural combinations. Keep a sealed final test split that the learning controller never accesses during development.

Suggested partitions:

- **Training episodes:** 50–200 trials per seed, used to generate evaluated structural updates.
- **Development episodes:** 20–50 trials for policy selection and regression checks.
- **Held-out in-domain tests:** fresh instances and combinations not used to derive rules.
- **Cross-domain tests:** a different surface domain with partly shared constraint structure.
- **Adversarial tests:** cases where superficially similar structures require incompatible actions.

These counts are illustrative planning ranges, not power calculations. Final sample sizes should follow a pilot-based variance and power analysis. Report generator seeds and hold out the test generator configuration when possible.

## 9. Metrics and Decision Criteria

### 9.1 Primary outcomes

**Held-out task success rate** measures correct solutions under all stated constraints. **Constraint violation rate** captures invalid plans. **Cost-normalized utility** adjusts for token use, calls, latency, and external tool costs. **Learning-curve area** measures improvement over the episode sequence.

### 9.2 Transfer and durability

Measure **cross-template transfer gain** relative to the fixed pipeline, **cross-domain transfer gain** on shared structural cores, and **retention after restart** with frozen units reloaded and only approved structural artifacts preserved. A **negative-transfer rate** counts cases where learned routing or reuse performs worse than the matched baseline.

### 9.3 Attribution and governance

Track policy-version lineage, evidence completeness, rejected updates, independent replication rate, and **counterevidence utilization**: how often a previously recorded failure prevents an analogous later error. Track false-positive capability promotions and confidence miscalibration separately.

For paired test tasks, use bootstrap confidence intervals or suitable paired tests, report effect sizes, and predefine a smallest practically meaningful gain. Correct for multiple comparisons when many variants are tested.

## 10. Testable Hypotheses

**H1 — Frozen-unit structural learning.** E3 achieves a positive, reproducible held-out gain over B1 at a comparable compute budget. **Falsifier:** no meaningful gain after matched-cost controls and repeated seeds.

**H2 — Routing attribution.** E1 improves task success on heterogeneous task families over B3. **Falsifier:** learned routing does not outperform random or simple fixed heuristics.

**H3 — Structural verification.** E2 reduces constraint violations on unseen tasks without an unacceptable cost penalty. **Falsifier:** improvement disappears after accounting for added checking calls.

**H4 — Negative evidence.** E3 yields lower repeated-error and negative-transfer rates than A1. **Falsifier:** retaining counterevidence offers no detectable advantage or consistently harms selection.

**H5 — Valid feedback matters.** E3 outperforms A2. **Falsifier:** shuffled or corrupted outcome labels produce comparable gains, suggesting the apparent learning signal is incidental.

**H6 — Limited transfer.** A subset of learned rules transfers to a second domain with shared constraint structure. **Falsifier:** no benefit beyond domain-specific prompting or examples.

**H7 — Durable improvement.** Gains survive a fresh-session restart and removal of raw training transcripts while retaining approved structural artifacts. **Falsifier:** performance reverts to baseline or depends on hidden task-specific memory.

**H8 — Bounded growth.** Gains eventually plateau or reverse under some task shifts, revealing measurable applicability boundaries. **Falsifier of an overly broad claim:** evidence that purportedly universal rules fail under controlled counterexamples; this is a valuable result rather than a failure of the research program.

## 11. Credit Assignment and Causal Attribution

A multi-unit system can obscure which intervention caused a gain. Record the full execution trace, selected policy version, unit outputs, evaluator result, and proposed update. Use one-factor-at-a-time ablations for routing, decomposition, verification, and memory. Where feasible, randomize policy assignment across matched tasks or use crossover designs to estimate causal contributions.

A success attributed to collective learning must not be credited solely to the learning controller if a changed tool, longer context, improved evaluator, or data leakage could explain it. Conversely, improved system behavior does not require claiming that any individual execution unit has become more intelligent.

## 12. Structural Memory and Evidence Quality

A reusable precedent should encode the **conditions of applicability**, not just a successful answer. Minimal entries contain task-feature signature, proposed rule, outcome distribution, supporting and contradicting evidence, known residuals, version, and expiry or review trigger.

Negative evidence should be first-class. For example, a scheduling rule that prioritizes the shortest task may work under one deadline distribution and fail catastrophically when long tasks block dependent jobs. A sound relay retains both observations and marks the rule as conditional.

Memory growth is not inherently intelligence growth. Measure retrieval overhead, stale-rule rate, and the benefit of pruning. Compare compact structural summaries against equal-size raw transcript retrieval.

## 13. Relay Across Space and Time

**Spatial relay** occurs when one unit's error analysis becomes another unit's verification constraint or when an independent research team reuses a documented structural rule. **Temporal relay** occurs when outcomes from earlier episodes influence later routing or policy. Neither implies improvement without validated benefit.

A relay record should preserve origin, target context, interpretation, adoption decision, evidence, uncertainty, and observed utility. The sequence **transmission → interpretation → adoption → utility → durable growth** contains distinct gates; success at one stage does not establish success at the next.

## 14. Illustrative Walkthrough (Hypothetical)

Consider a scheduling task with three jobs: Job C depends on A, and Job B has a near-term deadline. The initial fixed pipeline repeatedly produces an infeasible order because the planner optimizes urgency without checking precedence early enough. A later evidence bundle records the failure and a candidate rule: *when a dependency graph is nonempty, perform precedence validation before final scheduling*.

The controller tests the rule on unseen dependency structures. If it improves feasibility without excessive cost, the rule is promoted to a versioned routing policy. A subsequent software-maintenance planning task has an analogous dependency structure; the system probes whether the rule transfers while preserving domain-specific regression-test constraints.

This is a **hypothetical mechanism illustration**, not an observed result. A successful transfer would support a scoped system-level learning claim; failure would identify a boundary and inform future candidate selection.

## 17. Minimal MVP and Phased Roadmap

**Phase 0 — Pre-registration.** Freeze the task generator, component versions, evaluation rules, budgets, hypotheses, and primary outcome. Establish deterministic checks and leakage safeguards.

**Phase 1 — Static baselines.** Evaluate B0–B3 over several seeds. Quantify the value and cost of coordination before introducing learning.

**Phase 2 — Bounded adaptation.** Enable E1 and E2 with versioned policies. Verify that updates come only from allowed evidence and do not change execution-unit weights.

**Phase 3 — Evidence relay.** Compare E3 against B4, A1, and A2. Include adversarial and negative-transfer tests; record failed updates and rollback events.

**Phase 4 — Transfer and restart.** Evaluate sealed in-domain and cross-domain tasks, restart all units, retain only approved structural artifacts, and test durability.

**Phase 5 — Independent replication.** Publish generators, frozen-unit specifications, anonymized traces where permitted, evaluation scripts, and positive and negative results. Invite alternate controller implementations.

## 18. Failure Modes and Counterarguments

**Compute masquerading as learning:** More calls or longer prompts explain the gain. Address with matched-budget baselines and cost-normalized metrics.

**Memorization masquerading as generalization:** Structural memory stores exact answers or near-duplicate examples. Address with template-level splits and compact-rule ablations.

**Evaluator leakage:** The controller learns shortcuts to a weak scoring function rather than robust task performance. Address with independent constraint checks and hidden adversarial cases.

**Centralized controller intelligence:** A powerful adaptive controller effectively solves tasks itself. Restrict controller actions, report its capability separately, and compare with a direct-controller baseline.

**Coordination overhead:** Additional communication and verification erase gains. Measure latency, resource cost, and failure rates alongside accuracy.

**Negative transfer:** Reused rules harm new domains. Preserve residual differences, enforce scoped applicability, and require target-context retesting.

**Goodhart effects and policy drift:** The system optimizes a proxy while degrading unmeasured outcomes. Use diverse metrics, regression suites, and rollback policies.

**Nonstationarity:** Tasks change faster than the system adapts. Evaluate adaptation lag and stale-rule detection.

**Unsupported AGI inference:** Narrow system learning does not establish open-ended general intelligence. Report only experimentally supported capability scope.

## 19. Open Questions

1. What is the smallest frozen-unit ensemble that can demonstrate reproducible, nontrivial structural learning?
2. How much of a learned routing policy is transferable across domains with different surface representations?
3. When is structural memory preferable to direct fine-tuning, and when is it inferior?
4. How should credit be divided among the planner, checker, controller, and task evaluator?
5. Can negative evidence improve exploration efficiency without suppressing useful novelty?
6. How can a system detect that a formerly useful structural rule has become invalid?
7. What limits the growth of a fixed-capability ensemble as task complexity increases?
8. Which results can be reproduced with heterogeneous models, deterministic software units, or human participants?
9. Can an external evaluator remain sufficiently independent as the system adapts?
10. Which relay artifacts are portable enough to support genuine cross-team collective learning?

## 21. Collective Learning Invitation

This case is an open experimental proposal. Useful contributions include simpler baselines, more demanding task generators, rigorous sample-size planning, reproducible failure cases, alternative causal attribution methods, compact evidence schemas, and independently replicated negative findings. Contributors are encouraged to state the conditions under which an apparent improvement disappears, not only those under which it appears.

A productive outcome need not be a large gain. A reliable demonstration that frozen-unit structural learning works only within narrow boundaries—or that it fails under matched-cost controls—would materially improve the research framework.

## 22. Conclusion

A minimal system-centric laboratory can test whether persistent structural adaptation improves a group of frozen execution units. The relevant empirical claim is deliberately narrow: **under specified conditions, an organization of unchanged units may learn through its mutable coordination, evidence, and relay structures**. This must be distinguished from single-model learning, static ensemble gains, one-off tool augmentation, and general intelligence.

The next research step is to implement the controlled comparisons, retain counterevidence, and determine which organizational improvements are reproducible, transferable, and durable. That evidence—not analogy alone—should decide how far the system-centric intelligence hypothesis can be extended.
